# AI 웹게임엔진 설계

> 2026-10-25 사용자 결정: 예전 엔진·게임은 그대로 두고, 게임엔진을 코드까지 처음부터 만든다.
> 엔진은 게임 규칙을 모른다. 게임의 규칙은 게임을 만드는 사람이 스크립트(코드)로 짠다 — 유니티·고도와 같은 방식.
> 이 문서가 기준이다. 바꿀 때는 이 문서를 먼저 고친다. 진행은 `PLAN.md`.

## 1. 원칙

1. **엔진 = 공통 기능 + 편집기.** 그리기, 오브젝트·컴포넌트, 입력, 소리, 시간, 자원, 저장, 네트워크, AI 호출. 어떤 게임의 개념도 엔진에 없다.
2. **게임 = 프로젝트.** 씬(오브젝트 배치) + 스크립트(규칙) + 자원(그림·소리·데이터).
3. **분업.** 엔진 기능 하나 = 모듈 하나. 오류·로그는 어느 모듈·어느 오브젝트·어느 스크립트에서 났는지 달고 나온다.
4. **AI(Claude 포함) 비용 최소.** 엔진이 검사·시험을 맡고, 스크립트 API는 작고 일정하게.
5. **화면 = 명령줄.** 편집기로 하는 일은 명령줄로도 된다. 화면 조작 시험으로 확인한다.
6. **엔진은 도구일 뿐.** 엔진 안에 게임 기능을 절대 넣지 않는다. 게임은 반드시 이 엔진(편집기 또는 명령줄)으로 만든다. 엔진으로 만들 수 없는 것이 나오면 게임에 우회 코드를 넣지 말고 **엔진 도구를 개선한 뒤** 만든다(어느 게임에나 쓸 수 있는 일반 기능으로).
7. **사람이 이해하고 통제한다.** 아래 8장 "사람 편집 원칙"을 따른다. AI가 구현하고, 사람은 의도·품질·최종 판단을 맡고, 편집기는 둘을 잇는다.

## 2. 핵심 구조 (유니티·고도 방식)

```
프로젝트
├─ 씬 (Scene)          화면 하나. 오브젝트 트리
│   └─ 오브젝트 (Node)  이름, 켜짐/꺼짐, 자식 오브젝트, 컴포넌트들
│        └─ 컴포넌트    기능 조각: 내장(글자·그림·버튼·입력칸·목록·소리·타이머…) 또는 스크립트
├─ 스크립트 (JS)        게임 규칙. 컴포넌트로 오브젝트에 붙는다
├─ 자원 (Assets)        그림·소리·글꼴·데이터(JSON)
└─ project.json         이름, 시작 씬, 켠 엔진 모듈, 설정
```

- **오브젝트 + 컴포넌트**: 오브젝트는 그릇이고 기능은 컴포넌트가 준다. 같은 오브젝트에 여러 컴포넌트를 붙인다.
- **스크립트 컴포넌트**: 생명주기 함수 `start()`, `update(dt)`, `destroy()` 와 이벤트 받기. 공개 속성(`props`)은 편집기 인스펙터에 칸으로 나온다.
- **신호(이벤트)**: 오브젝트·컴포넌트가 신호를 내고 다른 것이 받는다(고도의 signal). 게임 전체 이벤트 버스도 있다.
- **프리팹**: 오브젝트 묶음을 저장해 두고 여러 번 만든다.
- **씬 전환**: 한 씬에서 다른 씬으로. 씬을 겹쳐 띄울 수도 있다(팝업).

## 3. 엔진 모듈 (공통 기능)

| 모듈 | 하는 일 |
|---|---|
| core | 씬·오브젝트·컴포넌트·생명주기·신호·게임 루프(시간)·씨앗 있는 난수 |
| render | 그리기 (HTML/CSS 기반 2D: 배치·글자·그림·애니메이션). 화면 맞춤(고정 크기 늘이기 / 창 크기), 프로젝트 스타일 시트(`.css` 자원 — 게임 화면 안으로 범위를 가둠), 오브젝트 스타일 이름·CSS 변수 |
| ui | 내장 컴포넌트: 글자, 그림, 버튼, 입력칸, 목록, 패널(배치) |
| talk | 글로 주고받는 이야기 부품: 이야기 칸, 번호 선택지, 막대, 그림 위 구역 (`TALK.md`) |
| input | 클릭·터치·키보드·글 입력 |
| audio | 효과음·배경음 (소리 없으면 합성음으로 대신) |
| assets | 자원 불러오기·미리 불러오기 |
| state | 게임 전체 저장소(값이 바뀌면 신호), 저장·불러오기 |
| room | 함께 하기: 방 이름과 자리 열쇠, **서버가 판정**(게임의 규칙을 서버에서 돌린다), 자리마다 보이는 정보만, 받을 자리에만 가는 채팅 (`ROOM.md`). 2026-11-11: 처음 적었던 이름 'net'과 '방장이 판정'을 바꿨다 — 화면 하나가 판정하면 그 화면이 모두의 숨은 것을 쥐게 된다 |
| ai | AI 글 만들기 요청(저장소 먼저, AI는 마지막, 구독 CLI). 그 위의 세 도구: 글 → 게임이 허락한 후보(`propose`, 제안 → 검사 → 적용의 '제안·검사'), 사실 → 이야기(`narrate`), 인물로서 대답(`speakAs`) — 검사에 걸린 글은 버리고 게임의 틀 글 (`TALK.md`) |
| debug | 콘솔, 오브젝트·상태 들여다보기, 오류 위치 |

모듈은 폴더 하나씩, 각자 시험을 가진다. 스크립트는 `engine.<모듈>` 으로만 기능을 쓴다(정해진 API).

### AI의 역할 구분 (사용자 확인 2026-10-25)

| 역할 | 언제 | 하는 일 | 지키는 것 |
|---|---|---|---|
| 규칙 AI (제작) | 편집기에서 만들 때 | 스크립트·씬·데이터 초안 | 엔진 검사·시험을 통과해야 저장. 저장 뒤엔 다시 안 부름. 좋은 모델, 드물게 |
| 실행 AI (게임 안) | 플레이 중 | 대사·묘사 같은 내용만 | 게임 상태를 바꾸지 못함(판정은 스크립트). 싼 모델, 저장소 먼저 → AI는 마지막 |
| 검토 AI | 자동 플레이 뒤 | 기록을 읽고 고칠 곳 제안 | 반영은 편집기·명령줄을 거침. 가끔 |

엔진에서는 실행 AI = `ai` 모듈(스크립트가 `engine.ai.text(...)`로 부름), 규칙 AI·검토 AI = 편집기 도구. 모델 설정과 사용 기록은 역할별로 따로.

조사 반영 (2026-10-25, 근거는 PLAN.md 진행 기록):
1. **실행 AI는 사실을 갖지 않는다.** 사실(상태)은 스크립트가 갖고 AI는 말로 옮긴다. AI가 무언가를 바꾸게 하고 싶으면 게임이 허락한 함수 목록만 제안할 수 있고(구조화된 출력·함수 호출), 엔진이 **제안 → 검사 → 적용** 순서로 처리한다. 판정은 끝까지 스크립트.
2. **기억은 갈아 끼우는 부품.** 인물마다 고정된 성격(설정) + 대화 기억 + 아는 것 기억을 `ai` 모듈이 따로 보관하고, 부를 때 필요한 것만 넣는다(긴 기록을 통째로 보내지 않음).
3. **모델은 역할별 크기.** 실행은 작고 빠른 모델, 제작은 큰 모델. 결과는 저장소에 남겨 재사용.
4. **규칙 AI는 '분석 → 실행 → 확인' 순환.** 프로젝트 색인(스크립트의 이름·API 목록)을 주고 전체 파일을 읽히지 않는다 → 만든 변경은 **차이(diff)를 보여 주고** 사람이 승인 → 엔진 검사·시험·실행 기록으로 확인. 엔진 API 설명서는 짧게 유지해 AI에게 그대로 준다.

## 4. 편집기

```
┌ 메뉴·툴바 (▶ 실행, 저장, 새 씬, 빌드) ─────────────────┐
├ 계층(씬 오브젝트 트리) ┬ 씬 뷰 / 게임 뷰 / 스크립트 편집 ┬ 인스펙터(컴포넌트) ┤
├ 프로젝트(씬·스크립트·자원 파일) · 콘솔 · 디버거 ───────────┤
```

- 계층: 오브젝트 만들기·끌어 옮기기·복제·지우기.
- 인스펙터: 컴포넌트 붙이기·떼기, 칸 고치기(스크립트의 공개 속성 포함).
- 씬 뷰: 배치를 눈으로 보고 고친다. 게임 뷰: ▶ 실행.
- 스크립트 편집: 파일 열기·고치기·저장(문법 검사). 스타일 시트(🎨 .css)도 같은 곳에서 고친다(괄호 짝 검사, 편집 화면에 바로 반영).
- 📊 데이터: 데이터 파일(.json)을 칸으로 고친다. 설명 파일(.schema.json)이 있으면 한국어 이름·단위·범위.
- 오브젝트: 이름·태그·스타일 이름(스타일 시트의 .이름). 위치와 크기에 기준점(창 크기에 맞출 때)과 '스타일 시트가 정함'.
- 저장마다 검사·백업·기록.

## 5. 서버 (Python 표준 라이브러리)

편집기·런타임 파일 제공, 프로젝트 저장소(검사·기록·되돌리기), AI 요청 대리(구독 CLI), 빌드(게임을 파일 묶음으로 내보내기).
함께 하기는 **따로 뜨는 놀이용 서버**(`server/play.py` + 노드에서 도는 방 주인 `server/room_host.js`)가 맡는다: 게임 하나와 방의 길만 내주고 편집기의 길(쓰기·지우기·되돌리기·AI)은 갖지 않는다 (`ROOM.md`).

## 7. 하지 않는 것

- 예전 엔진의 코드·자료를 가져오지 않는다. (예외: 예전 게임과 같은 게임을 만들기 위해 그 **게임 내용 데이터**는 게임 프로젝트로 옮긴다 — 사용자 목표 2026-10-25)
- 게임 규칙(어떤 장르의 개념이든)을 엔진에 넣지 않는다. 필요하면 게임 쪽 스크립트·프리팹으로 만든다.
- 유니티·언리얼만큼 방대한 편집 화면을 미리 만들지 않는다. 기능이 생길 때 그 기능에 필요한 편집 도구를 함께 만든다.
- 모든 코드를 노드 그래프로 바꾸지 않는다. 시각적 로직은 흐름을 보여 줄 가치가 클 때만(나중 후보).
- 내부 구현용 값까지 편집기에 꺼내지 않는다.

## 8. 사람 편집 원칙 (Human-in-the-Loop, 사용자 지정 2026-10-25)

**이중 인터페이스, 하나의 데이터.** 같은 기능을 AI는 명령줄(`tool.py`)·코드로, 사람은 편집기 화면으로 고친다. 둘 다 같은 프로젝트 파일을 고치고, 같은 저장 기록(백업·되돌리기)에 남는다. AI용 엔진과 사람용 엔진을 따로 만들지 않는다.

| 하는 일 | AI 쪽 | 사람 쪽 (편집기) |
|---|---|---|
| 기능 만들기 | 스크립트 작성·수정 | 컴포넌트 붙이기·칸 설정 |
| 오브젝트 관리 | 씬 JSON·API | 계층 트리·끌어 옮기기 |
| 수치 조정 | 데이터·속성 값 | 인스펙터 칸 (단위·범위 표시) |
| 오류 분석 | 로그·오류 위치 | 알림 창에서 오브젝트·컴포넌트로 바로 이동 |
| 변경 확인 | 자동 시험 (`tool.py test/uitest`) | ▶ 실행·눈으로 비교·저장 기록 |

**규칙 (기능을 만들 때마다):**
1. **사람이 조정·검증할 값을 찾는다.** 속도, 횟수, 확률, 난이도, 문구, 배치, 연출 시간 같은 것. 이런 값은 코드에 박지 않는다. 스크립트 공개 속성(`props`)이나 데이터 파일에 둔다.
2. **값마다 의미·단위·허용 범위·기본값을 적는다.** `label`(한국어 이름), `help`(무엇이 바뀌는지), `unit`, `min`/`max`, `default`. 편집기는 이 정보를 보고 칸을 그린다.
3. **바꾼 결과를 바로 확인할 수단을 준다.** ▶ 실행, 씬 뷰 미리보기, 시험 시나리오 중 하나.
4. **내부 구현용 값은 꺼내지 않는다.** 사람이 바꿀 이유가 없는 값까지 칸으로 만들면 오히려 헷갈린다.
5. **AI의 변경은 사람이 이해하고 되돌릴 수 있어야 한다.** 저장마다 기록(메모 포함), 되돌리기, 바뀐 곳 보기.
6. **우선 적용 영역:** 게임플레이 수치, 씬 구성, 연출, 밸런스, 자원 설정, 수동 검증. 모든 함수·변수에 적용하지 않는다(비용).

**완료 조건:** 기능은 시험 통과 + **사람이 코드를 읽지 않고 그 기능의 조정 값을 찾고 바꿀 수 있을 때** 끝난 것으로 본다. 사람이 모든 내부를 알 필요는 없지만, 고칠 것이 어디 있고 바꾸면 무엇이 달라지는지는 알 수 있어야 한다.

**필요한 사람용 도구 (현황은 PLAN.md W11):** 씬·오브젝트 편집(있음), 인스펙터(있음, 단위·범위 표시), 데이터 파일 편집 화면(있음: 📊 데이터, 설명 파일 `<이름>.schema.json`), 실행 제어·들여다보기(일시정지·한 걸음·상태·값 바꾸기, 필요), 변경 전후 비교(필요), 실행 취소·이전 버전(있음), 시각적 로직(나중 후보).

## AI 기능의 설계 원칙 (2026-10-26, 사용자 지시)
엔진이 게임에 주는 AI 기능(`server/ai.py`·`draft.py`·`image.py`, `runtime/ai.js`)은 저장소의 개발 운영체계(`../AGENTS.md`, `../ai-ops/OPERATING_SYSTEM.md`)를 따른다: 설계·구현·검증 권한 분리, AI는 제안·점수·초안만 내고 확정은 규칙 코드나 사람이, 비용 계측과 상한, 실패의 자산화. 지금 코드와 어긋나는 곳과 고칠 계약: `../ai-ops/tasks/ENGINE-001/CONTRACT.md`.
